# Using LLMs for Legal Decision-Making in Austrian VAT Law: A Comparative Study

- 著者: Marina Luketina, Andrea Benkel, Christoph G. Schuetz (FH Oberoesterreich / JKU Linz)
- 年: 2026 (Journal of Business Analytics, DOI: 10.1080/2573234X.2026.2720626)
- タグ: RAG, fine-tuning, 法務, VAT, ドメイン適応

## 一言でいうと

オーストリア VAT 法の適用判断で RAG と fine-tuning を真正面から比べた論文です。RAG 単独が最も強く (textbook 93.24 %、実務 80 %)、fine-tuning は少し負け、両方の併用 (RAG+FT) は両単独より悪い (実務 55 %、textbook の理由付けの約 3 分の 1 が誤り) という「足し算が割れる」話です。検索が完璧なら 95.95 % まで伸びるので、律速は検索にあります。

## 背景・課題

- 税務相談の依頼は自然文で来るので LLM と相性が良いが、法務は hallucination が許されない領域です。VAT はほぼ全取引にかかり EU で調和されているので、汎用性のある良い検証対象です。
- 中心課題は課税地 (place of supply) の決定です。国内・EU 域内・非 EU で法源が分かれ、物品 (§3 UStG: 処分権移転地、輸送開始地) と役務 (§3a: B2B/B2C・相手の地位で分岐) で規則が違い、連鎖取引・三角取引などの例外が絡むと多段の法解釈が要ります。
- 先行研究は RAG か fine-tuning を単独で試すものが多く、同一条件での head-to-head 比較がありませんでした。特に「両方要るのか、RAG だけで足りるのか」は未検証でした。

## 提案手法

Wieringa の design science 流に、教科書事例 74 件を validation に回しながら設定を詰め、実務事例 20 件を test にする二段構えです。

- 検証対象: GPT 系に固定 (LegalBench で法務推論が最強だったため。単一ファミリーに絞って交絡を消す設計)。
- プロンプト: 課税地特定用と実務の一般分析用の 2 種。国は 1 つだけ、根拠条文の引用必須、回答はドイツ語、出力は JSON (理由付け→国の順。逆だと国と理由が矛盾する故障が出たため)。
- RAG (Azure AI Foundry): 法源は 2024-12-01 時点の UStG 本文・内国市場規則附属書・BMF 指令。Markdown 化→header/footer・相互参照の除去→chunk 化→top_k 件を {{contexts}} に挿入。課税地用は 5 文書、実務用は全文 36 文書。
- Fine-tuning: 758 問答 (講義ノート・税務士試験・Skriptum Umsatzsteuer 等。複合問は分解)。8 割で学習し教科書 74 件で評価、最後に全量で学習し直した最終モデルで本評価。
- Mocked RAG: 正解チャンクを直接渡す完全検索の上限。検索と生成の切り分け用。
- 長文脈対照: GPT-4.1 (100 万トークン) に法源全部入りプロンプト。

|---|---|
| 素の GPT-4o | 68.92 % |

- Mocked は 3 件外し (71/74)。検索さえ当たればほぼ解けるので、RAG の律速は検索です。FT を足しても Mocked は伸びません。
- 理由付けの人手評価 (Fig. 4、正解国の件のみ対象): Mocked は全件正解、RAG > FT、RAG+FT は約 3 分の 1 が誤り。誤りは (1) 推論は合っているが引用条文が違う、(2) 条文の型だけ真似て無関係な条文に当てはめる、の 2 型が支配的です。FT 単独は余計な情報を足して hallucinate する癖があります。

- RAG 対 FT の対応表 (Tab. 6) は [[12, 4], [2, 2]] (行 RAG 正/誤 × 列 FT 正/誤) で、McNemar (Yates 補正) p = 0.683、有意差なしです。n=20 では順位に確証はありません。
- 不一致の内訳に柄があります。RAG+FT の誤り 9 件は全部物品・うち 6 件が連鎖取引、FT の誤り 6 件も全部連鎖取引絡みです。学習パターンへの偏りが検索証拠を潰す、という読みです。RAG 単独の誤り 4 件はパターンが散っています。

- 著者らの留保: 単一プロバイダ (OpenAI のみ)、素朴 RAG、n=20、プロンプトは GPT-4o 用。実務の誤答率 2〜3 割は許容外で、最終責任は税理士 (human-in-the-loop) が持つ前提です。

## 実装メモ

LLM の学習は重いので、このリポジトリでは範囲を絞り、**主張の向きを合成データで確かめる小規模実装**を `src/vat_small.py` に置きました。依存は numpy のみです。

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python src/vat_small.py
```

実装の対応関係は次のとおりです。

| 関数 | 対応する主張 |
|------|--------------|
| `exp_table5` | Tab.5: mocked ≥ rag > ft > rag_ft > plain、degenerate 2 種は最下位 |
| `exp_chain` | §9.1: chain 難問では ft が崩壊し rag が保つ |
| `exp_mcnemar` | Tab.6: n=20 の paired 比較は有意差なし (Yates 補正 p) |

合成の仕掛けは各アプローチの正誤生成過程です (すべて仮定)。plain はタイプ別正解率、rag は検索 hit すれば正解・外せば plain 後退、ft は seen タイプに強いが chain (held-out の代理) に弱い、rag_ft は検索と学習パターンの衝突で正解を反転させる、mocked は oracle 検索＋稀な生成ミスです。majority (常に最頻国) と random は DEGENERATE 対照です。

実行結果は次のとおりです。

```

[Table.5] ft       small=0.838 paper=0.8919
```

### 縮小再現 (vat_mini、seed0、Qwen2.5-0.5B)

合成ドイツ語事例 (規則 12・train 1200・test 150) での 5 条件の実測です (test はタイプ×30)。

```
plain  acc=0.447 strict=0.387 (学習なし・文脈なし)
rag    acc=0.173 strict=0.160 hit=1.0 (学習なし+検索)
mocked acc=0.180 strict=0.167 hit=1.0 (学習なし+正解 chunk)
ft     acc=0.913 strict=0.913 (LoRA・chain 除外学習)
rag_ft acc=0.940 strict=0.940 hit=1.0 (LoRA+検索)
```

タイプ別 (ft / rag_ft): b2b 1.00/0.91、b2c 1.00/1.00、chain 0.50/0.77、goods 1.00/1.00、transport 1.00/1.00。

- 論文と一致: ft は seen タイプで満点だが held-out の chain で半減 (0.50)。FT の誤りが連鎖取引に集中する §9.1 の向きと同じです。検索を足すと chain が 0.77 まで戻り、全体も 0.940 に上がります。
- 論文と不一致: 併用 (rag_ft) が ft を上回りました (0.940 > 0.913)。論文の「併用が両単独より悪い」は出ていません。ただし b2b だけ 1.00→0.91 に下がり、衝突コストの片鱗はあります。検索 hit=1.0 の合成設定では文脈が純粋な助けになり、論文の実務条件 (検索不完全・20 件) とは土俵が違います。
- 無学習 0.5B では文脈追加が有害でした (rag/mocked が plain を下回る)。検索品質の問題ではなく (hit=1.0)、小さな素モデルが長文脈をさばけない側です。論文の長文脈 GPT-4.1 の不振 (81 % < RAG) と同型の向きです。
- 留保: 単一 seed・test 150 件。seed 拡張は 30b 再走と枠が重なるため未実施です。

## 日本の消費税法での小規模検証 (`jp_vat/`)

論文はオーストリアの付加価値税 (VAT) ですが、同じ問い (RAG と FT は法的判断でどう効くか) を、日本の消費税の**内外判定** (国内取引か国外取引か) で小規模に確かめました。検索の作り方 (chunking、ハイブリッド、参照グラフ、書き換え、rerank、small-to-big、埋め込みの追加学習) も、同じ土俵で比べています。

### 設定

- 法源: 消費税法 4 条、消費税法施行令 6 条、消費税法基本通達 5 章 7 節の計 48 unit (項・号・通達番号の単位)。e-Gov 法令 API と国税庁のサイトから取得します (`fetch_sources.py`)。法令・通達は著作権法 13 条により権利の対象外です。
- 事例は、規定から**決定的に生成**します (`cases.py`)。規定の種類 (family) ごとのテンプレートで、正解 (国内 / 国外) と根拠 (unit) が機械的に決まります。**条文の読みを私が符号化したもので、税務の専門家のレビューは受けていません。**

| 分割 | 件数 | 内容 |
|---|---|---|
| train | 800 | seen の family。学習に使う |
| dev | 200 | 検索の設定を選ぶ |
| test_seen | 160 | seen の family。言い回しと地名が学習に出ない |
| test_exc_seen | 45 | 学習に出る例外 (通達 5-7-1、5-7-10、5-7-12) の新しい事例 |
| test_exc_unseen | 60 | 学習に出ない例外 (通達 5-7-11 の船荷証券、令 6 条 2 項 6 号の国内外にわたる役務) |
| real | 9 | 国税庁の質疑応答事例 (消費税 04) の照会要旨。結論は人手で付けた |

- 出力は「根拠 / 理由 / 結論」の 3 行です。採点は、結論の一致 (acc)、根拠の一致 (cite)、両方 (strict) です。
- モデルは Qwen2.5-1.5B / 3B-Instruct (LoRA r=32、3 epoch、150 step、3 seed の平均)。学習なしの比較に、Claude Haiku 5.5 / Sonnet 5.5 (API) も使いました (seed は 1 回)。
- 条件は論文 Tab. 5 に対応します: `plain` (学習も文脈もなし)、`rag` (検索した chunk を挿入)、`mocked` (正解の unit を直接挿入。完全検索の上限)、`long` (法令・通達の全文を挿入)、`ft` / `rag_ft` / `mocked_ft` (LoRA 学習後の同じ条件)。
- 検索の成否は **hit_all** (正解の unit が全部、挿入した文脈に入ったか) で測ります。chunk は条文の単位 (unit) です。BM25 は文字 bigram、dense は BGE-M3 です。

### 検索の比較

dev で設定を選び、各分割の hit_all で報告します。`ctx` は test_seen で挿入した文字数の平均です。

| 検索 | dev | test_seen | test_exc_seen | test_exc_unseen | real | ctx |
|---|---|---|---|---|---|---|
| dense、k=8 (元の設定。dev で選んだ最良) | 0.82 | 0.89 | 0.36 | 0.78 | 0.22 | 1,832 |
| BM25、k=8 | 0.76 | 0.87 | 0.09 | 1.00 | 0.22 | 2,227 |
| ハイブリッド (RRF)、k=8 | 0.84 | 0.98 | 0.33 | 1.00 | 0.22 | 2,142 |
| dense + 参照グラフ、k=5、cap=6 | 0.85 | 0.89 | 0.62 | 0.88 | 0.56 | 1,943 |
| **ハイブリッド + 参照グラフ、k=5、cap=6** | **0.90** | 0.95 | **0.80** | 1.00 | **0.78** | 2,044 |
| LLM で書き換え + ハイブリッド、k=5 | 0.42 | 0.42 | 0.24 | 0.90 | 0.56 | 1,330 |
| LLM で書き換え + ハイブリッド + 参照グラフ | 0.67 | 0.60 | 0.69 | 0.98 | 0.89 | 1,954 |
| LLM rerank + 参照グラフ、k=5、cap=6 | 0.89 | 0.94 | 0.78 | 0.97 | 0.78 | 1,788 |
| small-to-big (段落、dense、k=3) | 0.67 | 0.75 | 0.24 | 0.67 | 0.00 | 2,650 |
| BGE-M3 の追加学習、k=5 | 1.00 | 1.00 | 1.00 | 0.98 | 0.67 | 891 |

- **参照グラフ**は、当たった unit が引用する unit (令・法・通達) と、引用してくる unit を足す方法です。ハイブリッドに足すと、例外 (test_exc_seen) が 0.29 から 0.80、real が 0.11 から 0.78 に上がります。挿入する文字数は、dense k=8 とほぼ同じ (約 2,000 字) です。例外の規定は、本則の unit を引用する形で書かれているため、一緒に取れると外れにくくなります。
- **クエリの書き換え**は逆効果でした (dev 0.75 から 0.42)。書き換えで、事例の事実関係の言い回し (地名、物の種類) が落ち、検索の手がかりが減ったためと見ています (原因の切り分けはしていません)。
- **LLM rerank**は、参照グラフ付きのハイブリッド (0.90) と同水準 (0.89) で、上積みはありません。
- **small-to-big** (小さい chunk で検索し、親の範囲まで広げて渡す) は、unit のままより悪く、挿入は長くなります (約 2,650 字)。
- **固定長の chunking** は、短い (150〜300 字) と、k=8 で hit が 0.56〜0.70 と、unit (BM25 で 0.76、dense で 0.81) より低くなります。600 字では BM25 が 0.87、1,200 字では k=8 で 1.00 になりますが、そのぶん挿入する文字数が増えます (k × 1,200 字、最大約 1 万字)。unit 単位は、短い文脈で当てる点が利点です。
- **埋め込みの追加学習**は、dev から real まで 1.00 に近く、見かけ上は最良です。ただし、事例がテンプレートから作られるため、学習用 800 件と評価用の事例は同じ型で、**分布内の漏れ**を含みます。型が違う real (9 件) では 0.67 で、参照グラフ付きのハイブリッド (0.78) に及びません。改善の根拠にはしません。

評価の件数は、test_seen が 160、test_exc_unseen が 60、real が 9 です。real の 1 件は約 0.11 にあたり、差は 1〜2 件分です。

- **ft は、学習に出た規定に強く、出ない規定は引用できません。** test_seen の strict は 0.77〜0.85 ですが、学習に出ない例外 (test_exc_unseen) では 0.00 です。結論の正解率は 0.73〜0.74 あり、根拠を書けない (cite 0.00) ことが原因です。論文の「FT は学習に出ない型で崩れる」(§9.1) と同じ向きです。
- **rag_ft は ft より劣る場合があります。** test_seen では、1.5B が 0.77 から 0.50、3B が 0.85 から 0.52 に下がります。一方、学習に出ない例外では、0.00 から 0.25 / 0.45 に上がります。検索が足りない部分を補う一方で、学習した型を乱すと見えます。論文の「併用が両単独より悪い」と同じ向きですが、ここでは ft が強い test_seen で出る現象です。
- **小さいモデルは、文脈を足すと崩れる場合があります。** plain の結論の正解率 (acc) に比べ、1.5B では rag が下がる分割があります (test_seen で 0.55 から 0.46)。長文脈 (long) は、小さいモデルでは strict が 0.00〜0.19 です。
- **Claude では長文脈が効きました。** long の strict は、Haiku で 0.93 / 1.00 / 0.44、Sonnet で 0.97 / 1.00 / 0.56 で、どの分割でも rag と同水準以上です。論文の「長文脈の GPT-4.1 は RAG に劣る」は、ここでは再現していません。法令の全文が約 48 unit と短いためと見ています。
- **検索の改善が、そのまま効きました。** Claude の rag から rag (hg) で、real の strict が Haiku で 0.33 から 0.56、Sonnet で 0.22 から 0.67 に上がります。mocked (0.89 / 0.78) が上限です。論文の「RAG の律速は検索」(Mocked RAG が 95.95%) と同じ向きです。

### 留保

- 事例は、規定からテンプレートで作ったものです。seen の評価は、言い回しと地名を変えていますが、型は学習と同じなので易しく、ft の強さを過大に見せている可能性があります。
- 条文の符号化は私が行い、税務の専門家による確認はありません。real の結論も人手です。
- real は 9 件のため、その列の数値は傾向としてしか読めません。
- Claude の評価は 1 回で、seed の揺れを見ていません。ft 系の平均は 3 seed ですが、標準偏差は表に出していません。
- 論文のオーストリア VAT の再現ではありません。法源も、問いの形も違うので、絶対値は比べられません。

## 所感

- 一番面白いのは RAG+FT の負け方です。直感 (足せば強くなる) に反し、しかも壊れ方が連鎖取引に偏る。学習パターンが検索証拠を上書きする、という説明は rankrag の specialist 崩壊 (生成の破壊) と同型に見えます。うちの rankrag_mini でも併用条件 (mix_*) の振る舞いが不安定だったので、規模が違っても出る話かもしれません。
- Mocked RAG の 95.95 % が検索律速を示す lines はきれいで、RAG 改善の努力配分 (検索 9: 生成 1) の根拠になります。
- 実務 20 件の p=0.683 は「RAG が勝った」と言いたいところを踏みとどまらせる良い例です。こちらの VAT 縮小再現でも test 件数と有意性の関係は意識したいです。
- 日本の消費税で試して、一番はっきりしたのは**検索の作り方の効き方**です。例外規定 (通達) は本則の条文を引用する形で書かれているため、「当たった unit が引用する unit を足す」だけで、例外の取りこぼしが大きく減りました (test_exc_seen の hit_all 0.29 から 0.80)。論文の「文書構造に沿った chunking」と同じ発想で、法令では**構造 (引用関係) を使う検索**が、書き換えや rerank といった LLM を足す工夫より効きました。
- Claude では、検索を良くした分だけ real の strict が上がり (Sonnet で 0.22 から 0.67)、完全検索 (mocked) との差が縮みました。「RAG の律速は検索」(論文の Mocked RAG 95.95%) を、別の法域でも裏づける結果です。一方、real は 9 件なので、傾向としてしか読めません。
- rag_ft が ft より悪い現象は、日本の事例でも出ました (test_seen で ft 0.77〜0.85、rag_ft 0.50〜0.52)。ただし学習に出ない例外では逆に、ft が 0.00 で rag_ft が 0.25〜0.45 でした。「併用は常に悪い」のではなく、**学習で覆える範囲では悪く、学習の外では助けになる**と読むほうが、データに合います。
- 長文脈は、法令の全文が約 48 unit と短いので、Claude では RAG と同水準以上でした。論文の「長文脈の GPT-4.1 は RAG に劣る」は、文書量が多い条件の話かもしれません。文書量を増やして (たとえば所得税法や法人税法を足して) 比べる余地があります。
- 疑問として残るのは、事例がテンプレート由来で、型が学習と同じ test_seen が易しすぎる点です。ft の強さと、埋め込みの追加学習の hit 1.00 は、その分を割り引いて読む必要があります。税務の専門家のレビューと、実事例の件数を増やすことが、次の課題です。
