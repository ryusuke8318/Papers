# RASER: Recoverability-Aware Selective Escalation Router for Multi-Hop Question Answering

- 著者: Yuyang Li, Zihe Yan, Tobias Käfer (KIT AIFB / 上海交通大学)
- 年 / 会議: 2026 / プレプリント (arXiv:2606.02488)
- タグ: multi-hop QA, adaptive retrieval, routing, 費用つき選択, Gradient Boosting

## 一言でいうと

多段質問応答で、全質問に PRUNE(橋渡しの実体を提案して再検索する)や IRCoT(反復検索)を回すのは費用が大きいので、「1 回目(one-shot RAG)の結果だけ」から、追加検索を回すかどうかを問いごとに決める軽量ルーターの論文です。入力は、1 回目の答え・検索スコア・質問文から作る 6 つの特徴量で、追加の LLM 呼び出しは要りません。2 行動(one-shot か PRUNE)の RASER-2 は GBM の分類器と閾値 θ、3 行動(one-shot、PRUNE、IRCoT*)の RASER-3 は経路ごとの F1 を予測する 3 つの GBM 回帰器と、トークン費用の罰則つき argmax で選びます。論文は、6 つの LLM と 3 つのデータセットで、always-PRUNE のトークンの 41〜49% で、近い F1 が保てると報告しています。

## 背景・課題

- 多段 QA では、質問の分解や反復検索で精度を上げる手法が多いですが、どれも LLM を何度も呼ぶので、トークン予算が厳しい場面では使いにくくなります。
- 論文は、まず「追加検索が効く質問は一部ではないか」を調べます(3 章、回復可能性の分析)。質問ごとに one-shot、PRUNE、IRCoT*、Self-Ask* を全部回し、F1 を事後に比べると、one-shot で既に正解の質問が 24〜53%、どの手法でも直らない質問が 14〜27%、追加検索で F1 が 0.1 以上上がる質問が 14〜38% です(Table 1、6 つの LLM)。
- したがって、課題は「もっと検索する方法」ではなく、「追加検索に費用を払う価値があるかを、安く見分ける方法」だと位置づけます。

## 提案手法

**3 つの経路**

| 経路 | 手順 | トークンの目安(論文) |
|---|---|---|
| one-shot RAG | 上位 k=10 の塊を検索し、1 回答える | 約 1.2k |
| PRUNE | LLM が橋渡しの実体を最大 2 つ JSON で提案 → 各実体で再検索 → 規則ベースの検証器(新規性 novelty、支持 support が 0.05 未満の枝を捨てる)→ 最終の合成 | 約 3.8k |
| IRCOT* | 検索結果から短い事実を 1 つ抽出 → 質問に足して再検索、を最大 3 回(LLM が DONE と言う、または新しい塊が前回と Jaccard 0.6 超で重なれば停止)→ 最終の合成 | 約 3.5〜5.5k |

**6 つの特徴量(Table 2)**。どれも 1 回目の後に、追加の LLM 呼び出しなしで作れます。

| 特徴量 | 定義 |
|---|---|
| confidence | 1 回目の答えと問いの形から作る規則ベースの信頼度(式は示されていません) |
| ans_len | 1 回目の答えの語数 |
| bridge_cues | 「X of the Y of Z」のような多段の言い回しに一致するか |
| score_gap | 検索スコアの 1 位と 5 位の差 |
| score_top1 | 1 位の塊とのコサイン類似度 |
| qtype | 問いの形(entity=0、date=1、yes-no=2、count=3、other=4)を規則で決める |

**RASER-2**: ラベル y = 1[F1_PRUNE − F1_one-shot > τ](τ = 0.1)。GBM 分類器(100 本、深さ 3、学習率 0.1、subsample 0.8)が p(BRIDGEABLE) を出し、p ≥ θ(θ = 0.20)なら PRUNE の答えを返し、そうでなければ 1 回目の答えを返します。

**RASER-3**: 経路ごとに GBM 回帰器を 1 つ、計 3 つ学習し、その経路で得られる F1 を予測します。選択は

r* = argmax_r [ f̂_r(s) − λ · c̄_r ]  (c̄_r は訓練分割での経路 r の平均トークン)

です。λ = 0 なら予測 F1 が最大の経路、λ を大きくすると one-shot に寄ります。付録 G では、λ を直接ではなく「訓練分割の always-IRCOT* のトークンの何割まで使うか」という予算(既定 0.60)で指定します。

## 実験と結果

- データ: MuSiQue(主)、2WikiMultiHopQA、HotpotQA(対照)。検索は Nomic-Embed-Text-v1.5、塊は 128 トークン・16 トークン重なり、上位 10。LLM は GPT-OSS-120B、Mistral-Small-119B、Gemma-3-31B、Llama-3.1-8B、Llama-3-8B、Phi-4-mini で、温度 0。評価の質問数は 1 つの LLM とデータセットあたり 200〜500 です。
- 主結果(Table 3): always-PRUNE は one-shot の約 3 倍のトークンを使うのに、F1 の向上は小さく不揃いです。RASER-2 は always-PRUNE から F1 で 0.026 以内に収まり、トークンは 39〜57%(要旨では 41〜49%)です。RASER-3 は、中規模のオープン LLM の MuSiQue と 2Wiki で、always-IRCOT* の F1 の 87〜97% を、トークンの 47〜62% で得ます。
- 小さい LLM ほど反復検索の利益が大きい(6.1 節)。大きい LLM は、検索結果を書き換えても元の正解を答える割合が高く(GPT-OSS-120B 38%、Llama-3-8B 9%)、記憶で答えているため、追加検索の余地が小さいと説明しています。
- 特徴量の重要度(Table 5): score_gap 0.38、score_top1 0.35、confidence 0.12、ans_len 0.12、bridge_cues 0.02、qtype 0.01。検索スコア 2 つで 0.73 です。
- 分類器のアブレーション(Table 6、7): RASER-2 は F1 の幅が 0.011、RASER-3 は 0.016 で、GBM が最良ではないが同程度。RASER-3 の Ridge は PRUNE を 5% しか選ばない。
- 閾値・予算の感度(付録 G): θ を 0.10〜0.30 で動かしても F1 の幅は 0.014。予算を 0.33 → 0.60 にすると F1 が +0.058、0.60 → 1.00 では +0.021 で、トークンは 50% 増えます。

## 実装メモ

- `src/raser_core.py`: LLM に依存しない部分。F1(SQuAD の正規化、別名の最大)、文区切りの塊分割(128 トークン、16 トークン重なり)、6 特徴量、PRUNE の検証器、ラベル、費用つき argmax、予算から λ を選ぶ関数、質問単位の交差検証、経路ごとの指標、oracle、回復可能性の分類、ブートストラップ。
- `src/raser_pipeline.py`: 3 つの経路の手順。LLM(`gen`)と検索(`retrieve`)を関数で受け取るので、偽の LLM でテストできます。質問のバッチ全体を段階ごとにまとめて LLM に渡します。
- `raser_mini/run_llm.py`: vLLM と bge-small-en-v1.5 による実行(Modal のコンテナ内)。`raser_mini/modal_app.py`: Modal の起動。`raser_mini/prepare_data.py`: データの抽出。`raser_mini/analyze.py`: ルーターの学習・評価と、論文の主張ごとの検証(CPU)。`raser_mini/diagnostics.py`: 補助的な集計。
- プロンプトは、論文の付録 B.1 に書かれた役割と出力形式を参考に、自分で書き直しました(論文の文面そのものではありません)。
- 論文が決めていない箇所の置き方:
  - `confidence`: 式が示されていません。「答えが『分からない』なら 0、そうでなければ問いの形ごとの事前値(entity 0.6、date 0.8、yes-no 0.9、count 0.7、other 0.5)に、答えの文字列が検索された塊に含まれるときだけ 0.2 を足す(上限 1.0)」としました。論文の例(図 1 と B.4 で、同じ「分からない」に 0 と 0.8)は互いに食い違うので、前者に合わせました。
  - `bridge_cues`: 論文の 3 つの例を含む 5 つの正規表現(「X of the Y of Z」、who…born…where、the country where、the director of …、所有格 2 回)で、一致すれば 1 としました。
  - `qtype`: yes-no(文頭が助動詞)> count(how many など)> date(when、what year など)> entity(who、where、which、what)> other の順の規則です。
  - IRCOT* の再検索の質問: 元の質問に、これまでの事実を空白でつなげたものです。最終の合成は PRUNE と同じプロンプトで、文脈は最大 15 塊です。
  - 費用: 各経路のトークンは、その経路が使った LLM 呼び出しのプロンプトと生成の合計で、PRUNE と IRCOT* には 1 回目の分を含めます(論文の c̄ が one-shot 1,222、PRUNE 3,819 なので、含める解釈です)。
  - 予算から λ を選ぶ規則: 論文は「予算を満たす最大の λ」と書きますが、λ が大きいほど費用が減るので、「予算以内に収まる最小の λ」(予算の範囲で最も多く使う設定)と解釈しました。訓練分割の予測は学習に使った行の予測(訓練内)です。

### 小さい LLM ほど反復検索の利益が大きいか

利益 = その経路の F1 − one-shot の F1。同じ 1,500 問での 3B と 7B の差(対応ありの再標本)を示します。

| 範囲 | 経路 | 3B の利益 | 7B の利益 | 差(3B − 7B) |
|---|---|---|---|---|

### 実行の費用

- 動作確認(smoke、各データセット 12 問): 1 データセットあたり 3〜8 秒で、1 問あたりのトークンは one-shot 約 1.1k、PRUNE 約 3.7k、IRCOT* 約 3.6〜3.9k でした(論文は 1.2k、3.8k、3.5〜5.5k)。この結果から、全体を「1 モデルあたり約 12 分(読み込み約 3 分を含む)、2 コンテナ」と見積もりました。
- 本番(1,500 問 × 3 経路 × 2 LLM): 実測は、1 データセット 500 問の LLM 実行で 94〜199 秒(2 つのコンテナで 2 倍ほど違い、LLM のサイズの差と考えられます)、全体で各コンテナ約 12 分でした。
- 費用は、VRAM 80GB の GPU(Modal の `gpu=` で指定)を 1 時間約 2.5 ドルとして、本番が約 0.4 GPU 時間(約 1 ドル)、動作確認 2 回が約 0.3 GPU 時間(約 0.8 ドル)、合計で約 2 ドルと見積もります。上限の 5 ドルの範囲に収まっています。請求額そのものは確認していません。

## 分かったこと

- 追加検索の効く質問は一部(21〜27%)で、全質問に PRUNE を回すと 3.3〜3.4 倍のトークンを使うのに、F1 の向上は +0.024〜0.036 です。論文のこの枠組みは、小さな Qwen2.5 でも成り立ちました。
- RASER の「トークンを約半分にして F1 を保つ」は、7B では確認できました(トークン 45% で、always-PRUNE との差は -0.003 [-0.017, 0.012] で、無作為な昇格より +0.025)。3B では、F1 はやはり保てますが、そもそも PRUNE の利益が小さい(+0.024)ので、無作為に昇格しても期待値が近く、ルーターの上積みは +0.008〜0.010 にとどまります。「保てる」ことと「ルーターが効いている」ことは別なので、無作為の基準との比較が必要です。
- oracle との差は大きく(F1 0.45〜0.48 に対して RASER-3 は 0.34〜0.38)、6 特徴量で取れるのは、one-shot から oracle までの差の 3 割前後です。
- RASER-2 の判断の中心は、検索スコアの 2 特徴量(重要度 0.71)で、これは論文と同じです。ただし、特徴量を 1 つ抜いても F1 はほとんど変わらず(3B は差 0.004 以内)、特徴量の間に冗長性があります。bridge_cues と qtype だけでは、無作為な昇格とほぼ同じ(0.286 対 0.285)でした。
- 分類器の選択は、F1 に 0.005〜0.018 しか影響しません。論文の「特徴量が効いており、モデルは副次的」という結論と整合します。
- 反復検索の利益は、小さい LLM ほど大きいという主張は、この検証では確認できませんでした。7B は「分からない」と答える割合が高く、検索を追加すると答えられる質問が多かったためと考えられますが、原因の切り分けはしていません。

## この実装がカバーしない範囲

- Self-Ask*、ChainRAG は実装していません。そのため、Table 1 の分類と Table 3 の比較は、3 経路だけの値です。
- LLM は Qwen2.5 の 3B と 7B の 2 つだけです(論文は 8B〜120B の 6 つ)。大きい LLM との比較(c)は検証できていません。記憶への依存を調べる実験(6.1 節、Table 4)も行っていません。
- 検索器は bge-small-en-v1.5 です(論文は Nomic-Embed-Text-v1.5)。コーパスは、抽出した 500 問の候補段落だけで作っています(論文のコーパスの作り方の詳細は不明)。
- 質問数は各データセット 500、各 LLM 1,500 です。F1 の絶対値(MuSiQue で 0.14〜0.24)は、論文の同規模の LLM(0.22〜0.38)より低くなっています。7B は「分からない」と答える割合が高く(MuSiQue で 0.63)、プロンプトの違いや、塊の分け方、検索器の違いが影響した可能性があります。
- IRCOT* の停止条件(Jaccard 0.6 超)は論文どおりですが、2 回以上回るのは 36〜55% の質問でした(`docs/diagnostics.md`)。論文の IRCOT* より早く止まっている可能性があります。
- 特徴量 `confidence` の式と、回復可能性の「正解」の境界(F1 ≥ 0.5)は、論文が示していないので、私の解釈です。結果の絶対値はこれらに依存します。
- 区間は質問の復元抽出によるもので、質問の抽出(種 0 の 1 回)による揺れ、LLM の揺れ(温度 0 の 1 回)は含みません。ルーターは、LLM ごとに 1 回ずつ学習・評価しており、LLM をまたいだ汎化は見ていません。
- XGBoost、LightGBM、CatBoost は使っていません(HistGradientBoosting で代用)。ChainRAG の代替実験は行っていません。

## 所感・疑問点

- 論文の主張の中心(追加検索は一部にだけ効き、費用は約 3 倍)は、小さなオープン LLM でもそのまま確認できました。一方で、ルーターが無作為な昇格より良いかを、論文は示していません。この検証では、7B では明確に良く、3B では差が小さいという結果でした。無作為との比較を、表に入れてほしいところです。
- 要旨の「41〜49%」と、本文の「39〜57%」の範囲が違います。どの設定を指すのか、論文からは分かりませんでした。この検証では、45% にそろえた比較と、既定の θ・予算での比較の両方を出しました。
- 論文は予算を満たす「最大の λ」を選ぶと書いていますが、λ が大きいほど費用は減るので、「最小の λ」の誤りか、予算の意味が異なるのか、確認が要ります。
- `confidence` の式が示されておらず、図 1 と付録 B.4 の例(どちらも「分からない」)で 0 と 0.8 と食い違っています。式を示してほしい特徴量です。
- 小さい LLM ほど反復検索が効くという説明は、記憶への依存で説明されていますが、この検証では、LLM の保守性(「分からない」と答える割合)の方が、利益の差に効いている可能性があります。切り分けるには、同じ家族で 3 つ以上のサイズが要ります。
